# Qwen evidence v2 失败复盘与修订建议

本轮最早的偏差发生在动作选择和经验应用阶段：模型没有先决定“下一动作需要什么证据”，而是读入旧轨迹策略后持续重建几何。新工具把取数变方便了，却没有替模型解决“哪个点有意义、何时证据足够”的判断。此外发现一项可确定复现的工具参数缺陷。尚不能把三次失败归结为单一原因。

等待包含模型服务、传输和客户端过程，不是纯网络时间；工具可能并行，两列不能简单相加当作互斥的墙钟分解。任务 0 还有未完成请求，其等待不计入已完成请求合计。

**工具缺陷已确认**：`sensor_patch_batch` schema 允许 `radius=0`，源码却要求至少三个有效样本；单像素不可能满足。任务 0 四次调用共 20 点都因此返回逐点错误。全有效合成平面也能复现，而同位置使用现有半径 1 可计算。

上一份报告“无工具执行错误”仅指顶层错误，遗漏了嵌套的逐点错误，需要更正。原始 0/3 是尝试的记录结果；任务 0 现在标为受实验工具缺陷影响，不作干净的有效性失败样本。未触发该缺陷的任务 4/8 均为有效超时，成功率 0%（0/2）。受影响尝试不删除；修复后应另记补跑。

## 为什么新经验没有起作用

完整索引实际到达模型：任务 0/4/8 分别有 21/12/25 次请求携带两条新索引条目。它们不是被截断或未挂载；模型选择了旧经验，三轮都没有读取两篇新正文。

索引有 213 个链接、32627 字符。旧任务记录提供更具体的动作叙述，有些还带固定轨迹数值和过度推广的禁令。任务 8 实际读取的历史文字禁止 learned pick、要求手动抓把手，随后发生 22 次批量扫描。这支持“旧策略干扰新判断方法”的解释，但没有反事实试验证明因果。任务 0 的旧经验反而提到从初始姿态 learned pick，因此也不能把所有失败解释成旧经验禁止动作。

用户提示词另有一句“定位目标和目的地，然后执行”，会使后续放置几何看起来像首次抓取前的必要条件。任务 0 在尝试抓取之前先解决篮口，符合这个潜在冲突。建议只替换该句，不堆积更多提示。

## 是坐标错误还是规划错误

已用原发布版本对 40 次调用、267 个点完整回放；返回逐值匹配。对其中 247 个有效点独立重算中位数，也全部一致。未发现这些样本的数值计算错误；这不等于已验证相机物理标定或目标语义正确。

任务 4 的记录展示了上游判断问题：模型声称把手位于杯身的正向一侧，却与自己记录的两点坐标关系矛盾；一些采样实际落在桌面、杯体或把手空洞附近。即便采到真实把手表面，它仍不是完整的抓取末端位姿。两次下降耗尽动作步数，残差为 0.0317 / 0.052 米，均未到位；模型也描述了夹爪跨在杯口。其他两次上移/预定位达到容差，不能说机器人完全不响应。仅靠这些记录不能断言具体是碰撞、IK 还是其他约束。

任务 8 的 176 个点都来自初始帧，12 个为完全相同条件下的重复样本，其余多数换了像素，仍未建立可以抓取的判断。问题不是单纯重复同一个点，也不是缺少批量计算能力，而是没有停止取数并转换为行动的标准。

## 等待如何放大问题

三轮已完成请求的平均等待分别为任务 0 的 12.95 秒、任务 4 的 20.90 秒、任务 8 的 10.79 秒。任务 4 最慢一次为 97.31 秒。模型等待占 300 秒预算约 95–98%，工具自身每轮合计约 8 秒；不是几何计算执行太慢。

任务 8 批量结果累计产生约 10.1 万字符，最后一次请求的已报告输入达到 108879 token（含缓存部分）。测量往返不断增加历史内容和等待成本。缓存 token 不等于免费或无延迟；这里没有单独测出上下文大小对延迟的因果贡献。加快 API 可以增加可用决策次数，但不能保证模型会从测量转向抓取。

## 建议与边界

先修复已确认的工具契约；再用独立候选将经验缩到三篇有适用条件的判断方法，并替换那句过宽的前置要求。原版、原工具发布版本和原始轨迹保留。暂不增加更多几何工具：目前已能执行计算，缺的是输入语义、策略选择和行动条件。

[完整修改草案](proposal.md)包含文件、前后内容、新经验全文和验证计划：修复后补跑受影响任务 0，再以两环境并行进行 v3 的三次筛选。尚未获得新范围批准，未修改或部署提示词、经验或工具，未启动新实验。

验证已完成：远程历史回放、独立数值复算、半径缺陷最小复现、原图与反馈交叉核查、索引实际请求检查；分析脚本 Ruff 通过，776 个受保护文件哈希与原工作台状态复核通过。未重跑完整单元或 Sphinx：本轮只有独立分析脚本和 Markdown 报告，没有生产代码或 Sphinx 页面变化。
